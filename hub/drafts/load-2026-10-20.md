# 부하 점검 (2026-10-20 새벽 1~2시, 운영 API)

사용자 결정: 운영, 사용자 적은 새벽, A~D. Upstash·Vercel 요금제가 무료이거나 모름 → **1000명은 빼고** 저장소 명령 약 3만 개 안에서.
도구: `scripts/sim-users/load.mjs`(room·rooms·model), `scripts/sim-users/load-voice.mjs`(실제 앱 브라우저 N개, 가짜 마이크). 이 작업 공간에서는 `NODE_USE_ENV_PROXY=1`.

| 점검 | 결과 |
|---|---|
| B. 꽉 찬 방 (16명 + 넘치는 20명 동시) | 고치기 전 **17명이 들어감**(동시에 들어오면 모두 15명을 봄) → 고친 뒤 정확히 16명, 20명 ROOM_FULL. 자막 73줄 빠짐·순서 꼬임 0, 물음 p95 0.3초, 들어가기 p50 1.6초(36명 동시) |
| A(축소). 4개 방 × 10명 동시 40초 | 오류 0, 빠짐·꼬임 0, 물음 p95 0.15초, 1,344요청 |

| C. 소리 연결(실제 앱 브라우저) | 4명: 12/12 연결 60초 유지·모두 소리 받음 · 6명: 30/30 45초 유지 후 이 기계 CPU(부하 11, CPU 2개)로 끊김 · 8명: 처음부터 끊김·재연결 반복 — **이 기계 한계**라 8~16명은 실제 폰으로 봐야 함 |

## 고친 것 (서버, 바로 반영)
- 방 물음마다 사람 수만큼 저장소 GET을 따로 보내던 것 → 한 번에(MGET). 16명 방 하나가 초당 약 250개 명령을 쓰던 것.
- 동시에 들어오면 정원(16명)을 넘던 것 → 들어간 뒤 다시 세어 정원 밖이면 물러남(재현 테스트).

## 알아 둘 것
- 소리는 모두가 모두와 직접 잇는 방식: 16명이면 연결 120개, 폰 하나가 15명에게 따로 보낸다. 실제 폰 8명 이상은 확인 전 — 기기 점검 또는 중계 서버(SFU) 검토.
- 1000명 동시는 저장소 명령 약 200만(2분)으로 무료 한도(월 약 50만)를 넘어 앱 전체가 멈출 수 있어 하지 않음. 요금제를 확인하면 다시.
- 같은 계정이 두 기기로 같은 방에 들어오면 방장은 나중 기기로 옮겨 간다(의도된 동작).
