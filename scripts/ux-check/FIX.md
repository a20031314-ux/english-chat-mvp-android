# 가상 사용자 문제 표시 — 바로 고치기

체감 점검(BRIEF.md)에서 인물이 문제 화면마다 남긴 표시(`/mark`)를 **그 채팅에서 바로** 고친다(사용자 2026-11-01 "난이도가 너무 쉽다면 어떤 부분이 그렇게 느껴졌는지 파악해서 바로 반영"). 다른 체감 점수·화면 문제는 예전처럼 보고만 하고 순서는 사용자가 정한다(RULES "사용자 체감 점검").

## 순서

1. `node scripts/ux-check/triage.mjs` → `hub/drafts/ux-marks-<날>.md`(이유별 수, 문제마다 문장·보기(정답 굵게)·인물이 적은 이유·고칠 자리).
2. 표시마다 **스크린샷을 열어 확인**한다(`tmp/ux/run/<인물>/<shot>`). 인물의 착각(맞는 판정, 이미 고친 것)이면 고치지 않고 보고서에 "안 고침 — 왜"를 적는다.
3. 이유별로 고친다:
   - `easy-decoy`: 고칠 자리의 데이터 파일에 그 조각의 **흔한 실수 꼴** 2~4개(활용·시제·일치·조사·격·전치사·어순·성수·닮은 철자). 맞는 대안(축약·존댓말 변형·동의어)은 넣지 않는다(RULES 11 ②). 문장구조는 `plain/`에 "확실히 틀린 것"도. 같은 열쇠의 다른 조각(대소문자 꼴)도 같이.
   - `hard-ambiguous`: 그 보기가 실제로 맞는 말이면 오답 데이터에서 빼고(plain에서도), 채점(typed-check `open`)이 받게 한다.
   - `easy-leak` · `easy-copy` · `easy-repeat` · `easy-level` · `hard-level` · `wrong-judge`: 규칙(코드)이 원인 — 고칠 자리를 열어 원인을 찾고, 한 열쇠만이 아니라 같은 모양 전부가 고쳐지게. 테스트를 하나 더한다(띄어쓰기 없는 언어 1 + 영어 아닌 라틴 언어 1, RULES 2).
4. `npm run -s test:curriculum` · tsc · eslint. 데이터만 바꿨으면 그 열쇠로 퀴즈를 다시 만들어(브라우저 또는 `buildQuiz`) 새 보기를 본다.
5. 보고서(`ux-marks-<날>.md`) 끝에 "고침" 절: 표시 → 고친 파일·키 → 새 보기 한 줄. hub/log에 `- 학습 점검: 표시 n개 중 고침 m · 안 고침 k(이유)`.
6. 다음 점검에서 같은 열쇠·같은 이유가 또 표시되면 사용자에게 먼저 알린다.
